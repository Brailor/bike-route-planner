# Spike: Transitous coverage for ÖBB/MÁV, and bike-carriage data

- Date: 2026-10-29
- Method: inspected the feeds Transitous imports (feed list: `public-transport/transitous` → `feeds/at.json`,
  `feeds/hu.json`; data: Transitous's processed-data mirror `https://api.transitous.org/source-data/processed/`, the
  download route its usage policy recommends instead of the API). **No `/plan` API calls were made**, see "Usage
  policy" below.

## Questions (README open questions)

1. How well does Transitous cover Hungarian rail (MÁV)?
2. How reliable is bike-carriage data (`bikes_allowed` in GTFS) for ÖBB and MÁV?

All the stations we checked are present: Wien Meidling, Bruck/Leitha, Ebenfurth, Deutschkreutz, Hegyeshalom,
Sopron, Győr, Tata, Budapest-Keleti/-Déli/-Kelenföld, Esztergom, Siófok.

## Findings

1. **Coverage: good on paper.** Austrian and Hungarian rail, including the cross-border lines (Hegyeshalom, Sopron,
   Ebenfurth), are in. The MÁV feed is a **community conversion**, not an official MÁV publication. It's maintained
   and fresh (updated 2026-10-27), but it's a single point of failure.
2. **`bikes_allowed`: no data.** None of the three rail feeds even has the `bikes_allowed` column (0 of 57,169
   trips). So:
   - Bike carriage can't come from GTFS. We need **category rules** (e.g. ÖBB S/R/REX/CJX: bikes generally allowed
     subject to space; RJ/RJX/IC/EC/NJ: reservation needed; MÁV categories similarly) plus **user corrections** (the
     M2 pattern, as the README already plans).
   - MOTIS's `requireBikeTransport=true` filter is probably unusable: with no data it could remove every train. To
     verify once API use is settled.
   - The route short names carry the category reliably enough for rules (AT: `S`, `R`, `REX`, `CJX`, `RJ`, `RJX`,
     `IC`, `EC`, `NJ`, `CAT`…; HU: `S`/`Sz` (regional), `IC`, `IR`, `G`/`Z` (fast/semi-fast suburban)…).
3. **Timetable year boundary.** The Austrian feed ends on **2026-12-12** (timetable change). Plans after that date
   need the 2027 feed. Handle "no service found" gracefully around the change.
4. **Licences unclear.** Transitous's `license.json` lists no SPDX licence for these three feeds. The Austrian data
   comes from a portal that requires an account and has its own terms. Check before self-hosting or redistributing.

## Usage policy (blocker for the public API)

Transitous's API policy says: only for **open-source, non-commercial** projects with the source published under an
open-source licence; send a `User-Agent` with app name, version and a **contact** (email or website); link
`https://transitous.org/sources/` visibly; and coordinate if you exceed ~720 `/plan` requests a day.

This repo is currently **private with no licence**, so we don't meet the policy yet. Options:

- **A.** Publish the repo under an open-source licence, add the attribution link, and send a `User-Agent` with a
  contact you choose. This is the cheapest option for prototyping M4.
- **B.** Self-host MOTIS with these same feeds (README "later" plan). No policy constraints, but more ops (and the
  Austrian rail feed needs a Mobilitätsverbünde account).

## Verdict

- Coverage isn't a blocker: MOTIS/Transitous stays the primary transit source for M4.
- Bike carriage is entirely our problem: plan **category rules + user corrections** from the start of M4.
- Decide A vs B before M4. No live journeys were queried yet; do a handful of `/plan` queries (Wien–Sopron,
  Wien–Győr–Budapest, Budapest–Esztergom) once that's settled.
